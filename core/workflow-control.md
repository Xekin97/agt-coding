# 工作流控制契约

## 1. 状态是唯一流程依据

单流程产品仓库的 `.planning/workflow/state.yaml` 是当前里程碑、阶段、活动角色和审批状态的唯一正式依据。显式采用[需求工作流](./workstreams.md)后，每个需求以解析器返回的作用域状态为唯一正式依据，原文件保留为项目级协调入口。聊天话题变化、角色建议或某个文件已经生成，都不能单独改变阶段。

状态只维护当前流程字段、开放事项 ID 和当前入口引用；任务详情与下一动作在当前交接/计划，授权正文与历次迁移在原始决策/历史记录。仍有效的授权保留 ID、范围及来源指针，执行相应操作前核对完整原文；不在状态中追加整篇旧报告或历轮授权副本。

保持现有字段和消费者兼容：整理前检查实际读取方与冻结引用，未知字段不能仅因看似历史而删除。已有产品的内联授权只有在来源可恢复、引用可达且读取方支持时才改为引用；不能自动覆盖状态或迁移 Profile。缺少可选入口时，从现有 Profile 路径和当前交接定位，缺少入口本身不构成新审批门槛。

## 2. 控制面与工作面

- 工作面：用户直接与当前专业角色讨论，并查看其完整原始产物。
- 控制面：阶段守门器读取状态、检查条件，并在用户明确授权后迁移状态。

守门器不位于专业内容传递链路中，不得转述或重新总结专业角色的完整交付。

## 3. 角色启动条件

先运行 `node <基座>/adapters/workstreams/agt-workstream.mjs context --project <当前产品 worktree>` 定位当前作用域。单流程保持原路径；并行需求读取返回的状态、注册表、历史和产物根目录，并持有该需求写入租约。解析失败时不得回退写项目状态。任意窗口均可发起工作流管理，管理操作不继承该窗口专业角色的写入范围。

每个 Skill 启动专业角色前必须检查：

1. 产品仓库与 `.planning` 是否存在；
2. 项目清单和 Profile 是否已锁定；
3. 角色注册表中是否存在符合规范的语义实例名；
4. 当前阶段的 `active_role` 和 `active_agent` 是否与本角色一致；
5. 必需的上游产物是否已经批准；
6. 是否存在阻塞性决策或变更请求；
7. 本轮任务范围、产物根目录及本角色允许写入的路径；历史交付不能因文件名相同而成为当前输出。

初始化阶段可以在项目清单尚不存在时运行。[Quick 任务](#quick-tasks)使用独立任务上下文，按其有界授权执行，不激活本节的阶段角色；其余专业阶段不得跳过检查。

## 4. 角色激活与命名

角色激活不是只创建一个运行线程，还必须建立用户可见身份：

1. 根据职责生成或接受用户指定的 `<role-prefix>-<person-name>` 名称；
2. 使用 `validators/validate-agent-name.sh` 校验格式，再检查名称有明确职责语义、在项目内唯一且不包含哈希；
3. 写入当前作用域角色注册表（单流程为 `.planning/agt/agents.yaml`），分别保存 `role`、`display_name`、可选 `runtime_name` 和 `runtime_id`；并行模式通过工作流脚本 `activate` 在共享锁下分配名称和写入，不能绕过项目内唯一性检查；
4. 将工作流 `active_agent` 更新为用户可见名称；
5. 调用 Codex 子角色时优先使用同一语义名；若平台字段限制连字符，使用下划线映射；
6. 对用户展示和角色间引用始终使用 `display_name`，不能回退到 runtime ID。

未完成上述步骤时，角色保持未激活状态。

## 5. 显式迁移

只有用户明确表达“提交本阶段验收”“进入下一阶段”或同等意图时，才调用阶段守门 Skill。守门器需要：

1. 显示当前阶段和原始专业产物链接；
2. 检查必需产物、交接单、未决决策和开放变更；
3. 只报告检查结果，不替专业角色补写内容；
4. 条件不足时保持状态不变；
5. 条件满足时展示目标状态；
6. 获得用户最终确认后更新状态并追加历史记录。

<a id="authorization-scope"></a>

### 授权对象与范围

需求理解确认、局部交付验收、阶段迁移、整个里程碑收尾和开启新里程碑分别判断。守门器核对[需求确认闭环](./role-contract.md#requirement-confirmation)及用户原始答复对应的对象、版本、范围和停止条件；agent 写下的 `CONFIRMED`、文档齐全或状态已为 `complete` 都不能替代用户授权。

- “通过”“下一步”或选项字母只承接当时明确展示的对象；局部 UAT 通过不扩大为整个里程碑验收，需求研发请求不自动授权新里程碑。
- 当前里程碑未获明确收尾批准时，新增需求默认在其范围内评估归属；开启下一里程碑须同时有前一里程碑收尾及新里程碑启动的明确授权，不能由编号、终态或角色建议推导。已有授权直接复用，缺少时只澄清必要的归属/启动决定。
- 连续执行授权按已约定范围和停止点执行，各次迁移仍检查条件；不要求重复批准已授权步骤，也不替用户批准尚未展示的重要选择。授权对象或状态冲突时暂停受影响迁移，回查原文，不扩大解释。

检查交接是否指向唯一的当前有效文档，未确认项是否有去向。UI 交付同时按[设计来源](./design-delivery.md#sources)核对交付用途与批准范围，不以原型批准代替正式设计批准。存在冲突或缺少确认来源时，只指出受影响条目并交原角色修订，不能代写专业内容。最终接受结论及必要有效依据保留；活动任务已失效的过程资料按整理协议清除，普通当前检查记录复用，不因同一未变化的确认往返不断另建文件。

## 6. 失败与回溯

问题应返回实际责任阶段：

- 产品范围或验收矛盾 → 产品策划；
- 视觉或交互定义缺失 → UI/UX 设计；
- 数据库、API 或架构问题 → 技术方案；
- 代码偏离批准方案 → 实现；
- 验证方法与契约不一致 → 验证方案。

活动任务内回溯只处理受影响内容，不自动废弃无关已批准产物；已封闭里程碑不回溯，新问题进入后续任务。

## 7. 恢复工作

新会话或上下文丢失后，按[上下文读取](./role-contract.md#context-reading)从锁定清单/Profile、角色注册表、当前状态和当前交接恢复；由开放事项索引定向读取相关决策、变更和授权。最近迁移按 `last_transition` 的 ID 查询；仅在冲突、缺失或回溯时扩展相关历史，不全量加载 `history.yaml`。无索引时按稳定 ID 检索原文；不得依赖上一段聊天摘要作为唯一依据，也不得因恢复更换语义名。

<a id="context-maintenance"></a>

## 8. 收尾与封闭后的边界

活动任务的内容整理按[责任编排](./document-maintenance.md#6-上下文压缩的执行编排)执行：各专业角色先收敛本轮正文，QA 核对最终版本，交付负责人检查范围和一致性，守门器同步正式状态。阶段所需交接不等于永久留存材料；最终结论及必要接受依据保留。

里程碑完成验收、文档处理和交付后封闭只读。后续里程碑继承已完成前序基线；Quick 也只在自己范围记录增量，不能回写封闭目录。新的缺陷进入新任务，不重新打开原里程碑。

过去未正确整理的历史仅在用户明确的一次性存量整改范围内处理。记录原完成结论、本批范围和真实执行者，清除无效过程资料后重新封闭；不更改原业务终态、不重新签署验收、不把已接受限制写成已修复。这一迁移例外不成为日常维护权限。

静态完整性、语义复核和独立接续效果分别报告；没有实际独立检查就标 NOT_RUN。文件打包、文件数量下降或入口变短不能代替整理验收。

<a id="quick-tasks"></a>

## 9. 小任务独立执行

显式采用 [Quick 协议](./quick-tasks.md)后，有界的小修复、小增强、测试、配置及文档任务使用独立任务记录；用户的明确实施请求即授权范围内的短计划、执行和针对性验证，无需另开里程碑或重复激活完整阶段角色。普通小任务可自动路由到 `$agt-quick`，已在执行的任务步骤仍留在原计划。

任务记录管理该任务状态、文档责任映射和实际执行回执；本契约的里程碑状态/审批仍是里程碑真源。Quick 中的产品、设计、技术变化必须写入本任务正式增量正文，由任务内责任角色处理，不能回写已封闭里程碑，未回落不能收尾。任务级角色复用现有定义，不修改原 stage、活动角色、迁移或历史验收；可引用已完成里程碑，也可独立存在。新业务/设计/API/数据决定与必需人工接受仍按原授权边界处理，超出范围时保留结果并升级受影响事项；不自动创建新里程碑。提交、推送和发布继续依各自授权执行。

Quick 完成前必须执行任务范围的语义整理：先由各责任项收敛正式正文，再登记 `compact` 回执，`finish` 检查当前正文、验收、整理版本及最终有效依据，不要求已废弃原件永久存在。默认恢复只读当前结论和证据指针，历史显式展开；接续试验未执行时单列 NOT_RUN。细则与输入格式由 [Quick 协议](./quick-tasks.md#上下文收尾与归档)统一维护。
