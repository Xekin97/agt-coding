# 工作流控制契约

## 1. 状态是唯一流程依据

产品仓库 `.planning/workflow/state.yaml` 是当前里程碑、阶段、活动角色和审批状态的唯一正式依据。聊天话题变化、角色建议或某个文件已经生成，都不能单独改变阶段。

## 2. 控制面与工作面

- 工作面：用户直接与当前专业角色讨论，并查看其完整原始产物。
- 控制面：阶段守门器读取状态、检查条件，并在用户明确授权后迁移状态。

守门器不位于专业内容传递链路中，不得转述或重新总结专业角色的完整交付。

## 3. 角色启动条件

每个 Skill 启动专业角色前必须检查：

1. 产品仓库与 `.planning` 是否存在；
2. 项目清单和 Profile 是否已锁定；
3. 角色注册表中是否存在符合规范的语义实例名；
4. 当前阶段的 `active_role` 和 `active_agent` 是否与本角色一致；
5. 必需的上游产物是否已经批准；
6. 是否存在阻塞性决策或变更请求；
7. 本角色允许写入的路径。

初始化阶段可以在项目清单尚不存在时运行；除此之外不得跳过检查。

## 4. 角色激活与命名

角色激活不是只创建一个运行线程，还必须建立用户可见身份：

1. 根据职责生成或接受用户指定的 `<role-prefix>-<person-name>` 名称；
2. 使用 `validators/validate-agent-name.sh` 校验格式，再检查名称有明确职责语义、在项目内唯一且不包含哈希；
3. 写入 `.planning/agt/agents.yaml`，分别保存 `role`、`display_name`、可选 `runtime_name` 和 `runtime_id`；
4. 将工作流 `active_agent` 更新为用户可见名称；
5. 调用 Codex 子角色时优先使用同一语义名；若平台字段限制连字符，使用下划线映射；
6. 对用户展示和角色间引用始终使用 `display_name`，不能回退到 runtime ID。

未完成上述步骤时，角色保持未激活状态。

## 5. 显式迁移

只有用户明确表达“提交本阶段验收”“进入下一阶段”或同等意图时，才调用阶段守门 Skill。守门器需要：

1. 显示当前阶段和原始专业产物链接；
2. 检查必需产物、交接单、未决决策和开放变更；
3. 只报告检查结果，不替专业角色补写内容；
4. 条件不足时保持状态不变；
5. 条件满足时展示目标状态；
6. 获得用户最终确认后更新状态并追加历史记录。

## 6. 失败与回溯

问题应返回实际责任阶段：

- 产品范围或验收矛盾 → 产品策划；
- 视觉或交互定义缺失 → UI/UX 设计；
- 数据库、API 或架构问题 → 技术方案；
- 代码偏离批准方案 → 实现；
- 验证方法与契约不一致 → 验证方案。

回溯只重开受影响内容，不自动废弃同一阶段中无关的已批准产物。

## 7. 恢复工作

新会话或上下文丢失后，角色从项目清单、角色注册表、状态、最近状态历史、开放决策、变更请求和交接单恢复。不得依赖上一段聊天的摘要作为唯一依据，也不得因恢复会话而更换既有语义名。
