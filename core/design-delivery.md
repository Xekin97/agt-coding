# 设计交付与重构协议

适用于 UI/UX、前端架构、前端实现和质量角色。处理设计交付时读取本协议的[来源](#sources)、[文案](#copy)、[接收与实现](#implementation)、[验证](#verification)；设计或整改时同时读取[设计质量](#quality)与[重构](#redesign)。具体产品内容按任务读取，不递归展开全部页面。

本协议落实[共同契约](./role-contract.md)，不改变角色权限或增加审批阶段。产品必需路径由锁定 Profile 决定；旧项目升级前不得仅因缺少新版文件就追加门槛，也不得静默迁移锁或状态。

<a id="sources"></a>

## 1. 唯一有效来源

产品的 `design/design-spec.md` 是设计任务入口，使用[设计规格模板](../templates/design-spec.md)编制；当前 `handoffs/uiux.md` 链接它。按页面/区域/状态定位来源，避免让后续 agent 从聊天、截图或历史摘要重建设计。

| 来源 | 负责的内容 |
|---|---|
| `design-spec.md` | 当前目标、交付用途、设计基线、版本/批准范围、运行与场景入口、区域/资源/文案定位、必须保持项和验收 ID |
| `copy.json` | 固定界面文案与动态文案模板的准确文本 |
| `theme.css` | Token 数值及必要语义，包括适用的字体、间距、色彩、层次与动效 |
| `prototype/index.html` 及资源 | 实际布局、样式和可操作状态；读取源 HTML/CSS，不只看截图 |
| `interactions.md` | 触发、反馈、状态转换、中断、错误和动效参数引用 |
| `responsive-accessibility.md` | 目标视口、布局变化、键盘/焦点及减少动效规则 |

交付用途在现有规格和交接中明确，不按文件名或保真度推定：

- **交互原型**用于确认信息、流程、场景和状态转换；其批准只覆盖这些内容。
- **正式实现设计**在有效视觉基线上落实上述交互，给出完整页面上下文、布局、准确文案、样式/资源、响应式与交互细节，达到前端可据此实现的程度。交接须定位该版本及其正式设计批准范围。

两者可以在同一套文件中演进，也可直接交付满足要求的正式设计；不强制另建目录、重画相同内容或新增审批阶段。已有明确覆盖正式设计的批准无需重复取得；只有原型批准时，继续完成正式设计并提交其审阅，不能直接转为前端实现依据。

- 每次交付用可恢复的 commit 或快照定位同一套设计，包含相关资源；记录影响结果的未提交修改。版本标签不能代替可恢复来源。
- 规格按 `PAGE-*` / `CAP-*` 组织区域和状态，使用局部验收 ID（如 `UIA-PAGE-001-01`）。文案键、原型标识、资源路径和操作步骤须可解析；文案原文、Token 值和详细状态只在各自来源维护。
- 用户当前明确要求决定设计目标；原型、文案、规格之间的矛盾由 UI/UX 统一修正。文件时间较新或截图看起来合理，均不能自行覆盖另一份要求。
- 当前可实现范围、待审范围、已失效范围必须明确。历史批准不代表新版批准，未完成的新版也不能让已被否定的旧设计继续有效。

<a id="quality"></a>

## 2. 设计质量与可交付性

- 从当前用户目标、主任务和仍有效的业务/品牌约束推导信息组织、视觉焦点、构图、字体节奏、色彩和表面层次。分析参考中可采用的设计关系，不机械照搬页面。
- 增量需求默认接入当前已批准设计及实际页面/组件，在规格中引用基线并标明保留与改动区域；仅沿用主题颜色不代表完成整页融合。用户明确要求重构或否定旧方向时按[重构规则](#redesign)处理受影响范围。
- 存在真实方向分歧时，对代表性页面探索有区别的方案并说明取舍；用户已经明确的方向直接落实。一致的 Token 不要求所有页面套相同卡片布局。
- 关键状态变化显式决定是否需要过渡；需要时定义起止、时长/缓动来源、中断和减少动效行为，即时切换有其适用原因。纯色、卡片或无动画本身不构成缺陷。
- 已确定的 UI 文案使用最终措辞；动态数据的样例标明来源和限制。布局检查包含适用的长内容、空态与移动视口，不以占位文字代替正式交付。
- 在实际浏览器检查视觉、响应式和交互，并检查原型、文案源、资源与规格一致。结果对照本轮目标改进，不以主观分数或截图数量代替质量。无法运行时记录未验证范围，不能仅审源码就宣称视觉通过。

<a id="copy"></a>

## 3. 文案直接复用

`copy.json` 使用 UTF-8 JSON，顶层 `static` 与 `templates` 均为键到字符串的映射，无相应内容时使用空映射。键在文件中唯一，两个映射不共用同一键；未改变含义的条目保持键稳定。具体示例见模板。

- 标题、按钮、说明、占位提示、空态、错误提示及有独立要求的可访问名称有明确键；规格记录它们的区域、顺序、显示条件及状态，不只列一张无位置关系的字符串表。
- 原型与工程代码均消费该来源。前端可按既有工程约定导入或生成文案资源，记录源版本及转换方式；生成副本不手工另写，产品运行不依赖对 `.planning/` 的访问。
- 固定文案不自行同义改写、翻译、增删提示或更换标点。明确要求的换行须保留；浏览器空白折叠等比较规则在验收条目中说明，不用宽松归一化隐藏实际差异。
- 动态模板使用 `{variable}` 占位符，变量含义、格式、缺值处理和测试样例在规格中说明；实际值来自应用模型。业务数据、用户内容和 AI 输出不硬编码成原型样例，也不绕过 API 契约与 DTO 转换边界。
- 文案作为文本渲染；富文本结构在原型中定义，不把可替换变量拼成未经转义的 HTML。已有本地化资源可以承接转换，不为本协议强制引入新框架。

<a id="implementation"></a>

## 4. 前端接收与实现

前端正式交接与实现前，核对正式实现设计的版本/批准范围、运行与状态复现、区域/文案/资源定位、交互与响应式约束。仅有交互原型时由 UI/UX 补齐正式设计，不能让开发自行补视觉。依赖需要时，可在授权范围内先行技术探索/接口设计，标明暂定输入；技术方案批准不替代正式设计批准。缺失或冲突只暂停受影响部分，接收核对记入原有方案或自检报告，不新增审批。

- 架构在 `technical/frontend.md` 映射页面/区域/状态到组件、路由和应用模型，并确定文案/样式/资源的复用或转换方式及检查方法。
- 开发读取相关原型源文件，优先复用可用 Token、资源、样式和结构，再忠实转换为批准技术方案内的组件。只凭截图或摘要重新创作文案、删减内容、统一不同布局均不属于实现自由。
- DOM 和组件拆分可以不同；必须保持准确内容、元素顺序、视觉层级、响应式与交互结果。难以实现时先尝试等价实现，仍冲突则说明差异和备选方案，不能静默降级。
- 先完成代表性页面/区域的内容、布局与状态核对，再扩展共享组件，避免偏差批量传播；不要求逐页追加用户审批。
- 提交 QA 前检查文案/控件/资源的缺漏与错位、布局/样式、已定义状态及关键过渡，修复已知基础偏差。使用已有浏览器能力为实际失败模式建立针对性检查，不能把高还原责任全部后移到 QA。

<a id="verification"></a>

## 5. 检查与证据

前端在 `implementation/frontend-validation.md` 记录自检，QA 使用既有覆盖矩阵/报告；以下计划、预算和结论就地维护，不新增角色、审批或一套测试管理文件。

### 5.1 先确定本轮范围

打开浏览器前，根据当前请求选择模式，写明验收/缺陷 ID、设计与实现版本、本次变化及受影响依赖。一个用例可以支持多条验收，不为每条 ID 重复执行相同路径。

| 模式 | 适用范围与完成条件 |
|---|---|
| 快速冒烟 | 检查当前改动涉及的关键路径能否运行；通过仅说明这些路径可用，不替代完整验收，也不排除本次改动的明确高风险边界 |
| 需求验收 | 覆盖本次批准范围的用户结果、必要失败路径及视觉/交互要求；新功能或设计交付默认使用 |
| 缺陷复验 | 重现原问题、验证修复及受影响的共享使用处；返工默认使用，不自动重测整站 |
| 探索测试 | 在用户请求或明确风险依据限定的区域寻找未知问题；先限定范围、时间/次数和停止点，不让所有验收都变成探索 |

在原有矩阵为本轮条目补足“场景/视口/数据 → 来源与定位 → 预期结果 → 检查方法/所需证据 → 已有证据及复用依据”。定位优先使用区域内可访问角色/名称、已有 ID；确有必要时补稳定区域标识，不要求全站所有节点增加属性。原型与实现的定位可不同，由前端在既有映射或验证报告中对应；不以 DOM 层级或 CSS 写法相同作为还原要求。

### 5.2 选择足以判定结果的方法

优先用能证明该条预期的结构化信号，批量查询相关字段并输出断言结果；不是每条都依次跑完所有层级，也不以整页 DOM、全量 computed style 或长日志替代大量截图。

| 检查对象 | 方法与限制 |
|---|---|
| 文案和元素 | 从批准来源取得期望，检查运行页面对应区域/状态的文本、可见性、数量、顺序、资源和可访问名称；不能只比较两个 JSON，或从实现反向生成期望 |
| 表单、导航和业务状态 | 从普通用户入口实际操作至所需状态，检查值、URL、焦点、选中/禁用状态及必要请求；要求持久化时验证刷新/重新读取。调试跳转或强制状态不能独自证明流程可达，属性存在或 HTTP 200 不能代替可观察结果 |
| 对齐、尺寸和溢出 | 在已定义视口检查可见元素边界、实际尺寸、相对位置及必要样式；存在滚动容器不自动等于缺陷，容差引用局部要求，不统一套用 ±2px |
| 构图、图片、遮挡及视觉观感 | 对照批准来源检查代表性页面/区域；结构断言通过仍不能代替必要视觉判断，截图或像素差异用于这些问题 |
| 交互与 Motion | 用操作序列和时间/状态记录验证切换、中断、焦点、卸载及减少动效；必要时录屏或采样帧。静态图、立即跳到终态或仅有定时器不能证明完整过程 |

### 5.3 视觉比较的适用边界

使用截图对照或自动 diff 时，对齐设计与实现的浏览器/系统、视口、DPR、字体、主题、语言、数据及状态，等待所需资源就绪。静态对照可以固定动画状态；动效验收另按真实过程执行，不能全局关闭动画后宣称动效通过。

先复用项目已有截图比较能力。差异较多时可由工具定位、合并异常区域，再查看必要区域及上下文；不默认让模型逐组件寻找像素差异，也不为一次验收引入新视觉平台。动态内容的固定/遮罩、抗锯齿容差须说明范围及依据，不能遮掉正在验证的文案、时间、错误态或布局。一个区域位移造成连带 diff 时先查共同原因，不逐块重复诊断。

自动 diff 只支持所捕获状态的视觉结论，不能证明功能、可访问性、动效或原设计质量；差异存在也不自动等于实现错误。仍需按验收检查重要视觉关系。基线来自批准设计；首次保存实现截图不等于还原通过，确认还原后才可用于后续回归。更新基线须对应新批准来源，不能靠接受当前截图掩盖偏差。

### 5.4 证据预算与去重

- 采集与长期留存分开：日常截图、trace 和重试附件默认写入 Git 忽略的运行目录，正式验收只挑选必要证据。按[产物保留规则](./document-maintenance.md#evidence-retention)处理临时、未决、正式与历史图片；测试不能直接覆盖冻结证据。
- 在本轮计划中简记预计场景、保存截图/送模图片的软上限及需要追加证据的条件。普通行为成功路径默认无需送图；视觉要求选择必要代表图，失败或无法确定的问题再补证据。不设全产品统一截图张数，不用预算省略必要视口、状态或验收。
- 同一版本、场景、数据、语言、浏览器、视口/DPR及动效条件的已有充分证据不重复采集；内容或条件变化、修复复验、方法故障及连续动效采样是合理例外。截图文件与送给模型的图片分别计数，本地 diff 不等于模型看图。
- 只把失败摘要、相关字段、必要图像和原件路径带入模型上下文；长输出留在证据文件按需定位，DOM 查询和日志输出也有成本，不能视为无限预算。
- 超过软预算时说明是哪条验收仍缺证据，优先复用、合并或缩小无关输出；已授权且必要的检查继续执行，不因此新增用户审批。新范围按原确认规则处理。

### 5.5 复验与结束

复用证据须匹配验收、版本及相关依赖/环境；记录本次变化和为什么不影响原结论。共享组件、样式或契约变化要纳入受影响使用处，不能只看改动文件数。独立 QA 可复用开发基础检查，但仍负责必要的用户流程及跨边界验证。

只因相关变化、新问题证据或检查方法故障追加执行。方法不匹配时修正方法并重验，保留最终有效结论，复验完成后清理已失效过程记录，不改产品预期来消除失败。达到本轮所需证据后停止扩测并交付；有缺陷则按现有授权修复/交接及复验，不因“已找到问题”就结束整个已授权任务。

报告区分通过、失败、未执行/证据不足、定义待澄清及范围外建议。每个当前必需条目都有匹配的充分证据且阻塞缺陷已解决，才能声明本轮范围通过；缺少证据不能因预算用尽而通过，也不能把局部通过升级为整个里程碑通过。剩余条目写清来源、影响、责任和下一动作；`PARTIAL` 或“还有其他组合”本身不是无限追加测试的任务。

记录条目 ID、版本/快照、方法、实际结果、未覆盖范围及原件位置；确定性差异直接给期望、实际和位置，不展开逐步观察流水账。试点对比同一范围的缺陷发现结果、误报、执行次数/耗时、保存截图与送模图片、实际读取/输出量；无 usage 则 token/费用未知，不从截图数推算节省比例。

问题沿现有责任边界回溯：设计缺失/矛盾回 UI/UX，技术方案冲突回技术设计，实现偏差回开发，检查方法错误回验证。首次试点在现有报告记录首次交付偏差及因还原产生的 QA 往返，不把主观喜好作为新增硬门槛。

<a id="redesign"></a>

## 6. 按当前要求重构设计

用户要求整改、重构或否定旧方向时，以本轮目标重新推导受影响的信息组织、布局、文案、组件、视觉及交互；不默认在旧设计上增量修补。复用与重建均以满足新目标为依据，不以保留旧结构或最小差异为目标。用户已明确的整改授权无需重复询问；业务范围扩展仍按共同契约处理。

1. 在当前规格/交接记录新要求来源、失效旧条目、影响范围和仍有效的约束；受影响旧条目立即标为失效/待替换，不等新版完成才停止沿用。
2. 在当前活动任务修改设计；封闭里程碑的设计只读并作为继承基线。保留最终有效批准范围，废弃设计及旧过程证据在收尾时清除，不制作恢复副本。
3. 按新目标同步更新原型、文案、Token、资源、交互、响应式、设计规格和交接；检查共享组件的所有受影响使用处。当前正文移除失效规则，同步仍有效的引用；不要求保留已废弃设计的恢复入口。
4. 检查产物之间的键、路径、状态和效果一致；列出受影响的前端方案、实现与验收预期，由对应角色更新。旧证据不能宣称新版通过。
5. 区分正在整改、待审与当前可实现范围，依据实际用户确认更新批准来源；下游接续前重新核对版本。无关范围可继续，已失效范围不能回退旧稿实施，未批准新稿也不能自动实施。

具体状态迁移仍遵循[工作流契约](./workflow-control.md)。本协议不增加第二套工作流状态文件，也不要求每次局部修改重做整个产品。
