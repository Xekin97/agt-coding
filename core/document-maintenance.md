# 文档整理与封闭协议

整理是对内容的语义收敛：各责任角色更新有效正文，删除无效资料。不是把资料移到 archive，也不是制作 zip、tar.gz、压缩 JSON 或恢复索引。日常读取遵循[共同契约](./role-contract.md#context-reading)，交付执行遵循[交付协议](./delivery.md)。

## 0. 以接续开发的 agent 为使用者

有效资料应让后续开发者理解交付了什么、为什么这样约束、如何实现和验证，以及还有哪些明确限制。文件体积、文件数、压缩率和摘要长度都不是完成标准。

里程碑是继承链：已完成 M001 → 基于 M001 的 M002 → 基于已完成 M002 的 M003。保留基线和本轮增量、替代关系，不复制前序里程碑，不在每轮收尾重新汇编整个项目。完成并封闭的里程碑只读；后续变化写在新里程碑或 Quick 内。

## 1. 整理时机与责任

- 活动里程碑中，各角色在实质修订收敛和交接前整理自己负责的内容；只调用受影响的角色，不为小任务强制整套角色流程。
- 收尾时先汇合本次交付范围的 workstream，固定候选，再由责任角色收敛正文，QA 核对当前验证，交付负责人检查一致性、引用、范围和封闭条件。
- 固定候选只限制本次交付，不暂停其他独立分支。源分支或 main 更新后重新核对受影响部分。
- 守门角色同步正式状态，不能替专业角色编写内容或代替用户接受。

## 2. 保留什么、删除什么

| 内容 | 处理 |
|---|---|
| 本轮有效需求、业务规则与决定 | 保留在产品正文，记录与继承基线的增量及替代关系 |
| 当前有效设计、文案、交互与资源 | 保留可实现的正式来源；删除废弃稿和重复副本 |
| 当前数据模型、API、架构与实施说明 | 保留有效技术约束及必要实现入口 |
| 当前测试、验收结果及必要证据 | 保留适用版本、方法、结果、范围、限制和回归入口 |
| 已修复且针对性验证通过的 bug | 删除描述、排查流水、旧失败日志/截图；有价值的回归测试留在工程测试中 |
| 废弃方案、重复交接、过期计划与被替代结果 | 提取仍有效内容后删除，不另存压缩包或恢复索引 |
| 未解决问题、未完成验证、待用户接受 | 保留实际状态、影响、必要依据、责任及下一步，不借整理关闭 |
| 用途不明的内容 | 原地保留交责任人判定，阻止受影响任务收尾，不阻塞无关任务 |

一份文件混合有效与无效内容时先更新权威正文，再删除无效部分。现有压缩包只提取独有且仍有效内容到对应正文或工程测试，随后删除。删除已确定无效资料无需为它制作快照、保留副本或创建新索引；不重写既有 Git 历史。

有效需求不能被代码现状自动覆盖。代码与已确认要求不一致时，区分已确认变更、实现缺陷和待确认差异；只有已确认变更可直接更新正文。设计还原不足不能整理成新的设计要求。

## 3. 阶段材料与最终交付

Profile 的阶段 `required_artifacts` 用于执行期接收，不表示永久留存。最终交付按 `workflow.final_artifacts` 及本轮实际有效资源核对，交接单和过程计划可在完成其用途后清除。

验收至少能定位事项、代码/产物版本、方法、实际结果和未覆盖范围。最终结论及必要接受依据保留；无需保存整个修订过程来维持完成状态。工具记录必须同步移除对废弃资料的依赖，不能删除文件后仍要求旧快照全部存在。

对于已接受的限制，保留当时结论及范围；未执行不写成通过，已修复未验证不写成完成。无 commit 时可用本轮相关文件摘要定位实际版本，不要求为每轮生成恢复包。

## 4. 测试与运行产物

日常截图、trace、重试附件和长日志默认进入忽略的运行目录。最终只保留支持当前验收的必要证据、批准的视觉基线、工程测试输入和未决事项所需内容。

测试不能覆盖已封闭里程碑的基线；需要新预期时在当前任务记录变更及其批准来源。已修复问题的旧失败附件应删除，回归测试继续覆盖其行为。

删除旧日志、修复链接和合并重复说明只做文档完整性检查。修改有效需求、契约、设计、实现或测试预期时才重验相关行为；不因整理导致无关业务测试反复失效。

## 5. 完成与封闭

完成检查包括：有效内容准确、继承关系明确、必要引用可达、当前验收匹配候选、未完成事项未被隐藏、未覆盖他人工作。语义判断由责任角色作出，工具检查不能证明全部业务正确。

里程碑完成验收、资料处理和交付后封闭只读。后续里程碑或 Quick 只能继承和记录自身增量，不回写已封闭目录。普通“整理文档”不能当作重新开放里程碑的权限。

过去未正确清理的存量资料可以在用户明确的一次性整改范围内处理。记录范围和原完成结论，各责任角色整理后重新封闭；不重开业务开发、不改变原验收结论。这是迁移例外，不成为日常维护机制。

## 6. 上下文压缩的执行编排

启用模型路由时沿用已有任务分类与真实执行回执；明确整理使用 documentation，复杂范围判断/语义复核使用 document-plan/document-review，静态文件与引用检查使用工具。历史类别名 archive-execution 仅表示静态整理操作，不要求文件打包。简单任务不强制多轮分派。

1. 核对继承基线、当前候选、开放事项及责任范围。
2. 产品、设计、技术、实现和 QA 各自更新本轮权威正文；跨角色差异交原责任角色处理。
3. 删除已判定无效的过程资料，同步消费者和引用；合并前集中检查本次交付范围。
4. 汇合当前结果、限制、验收和下一步到已有入口，不新建第二套台账。
5. 交付负责人复核，按交付协议合并并封闭。

`compact` 登记已经完成的整理，不自动写文档，也不是聊天上下文压缩命令。单会话可按责任分区串行执行，但不能虚构独立 agent 或 QA。只有实际运行的独立接续检查才能记录通过；未运行标 NOT_RUN，不追加无关审批门槛。

可用 `validators/measure-context.mjs` 对明确文件清单只读计量，字符数不等于 token/账单。新会话是否能正确接续比字数变化更有意义；不能为了缩短入口删除必要约束。
