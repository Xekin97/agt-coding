# Execute a bounded AGT task

Read [quick tasks](../../../core/quick-tasks.md), [shared contract](../../../core/role-contract.md) and the Quick exception in [workflow control](../../../core/workflow-control.md#quick-tasks). Use `../../../adapters/quick/agt-quick.mjs`; `--help` gives exact commands. Read the [task template](../../../templates/quick-task.json) only when creating or revising a task.

## Route and recover

- Treat `$agt-quick <request>` or a clear small implementation request as authorization to carry out that bounded task. Natural-language requests can use this path; the user need not memorize the command. Follow the granularity table in the protocol. A step of an existing task stays in that task.
- `list` and `status <id>` only inspect; use CLI `list` or `show`. Start recovery with the concise `show/resume` output and current sources; expand `--history` and individual evidence only for a specific question, rather than reading the whole task JSON or old logs. Check branch, dirty files, evidence and compaction freshness before continuing authorized work. Completed/cancelled/escalated tasks are not reopened by resume. A blocked task needs its blocker resolved before `start --reason`.
- Inspect the product manifest, locked Profile, adoption configuration, workflow state, current handoff and applicable policies. A locked older framework needs an explicit compatible adoption; never silently load sibling HEAD contracts. Reuse adoption already authorized by the user. Workstream-enabled products currently use their requirement workflow and leases; this Quick implementation refuses writes in that mode.

## Implement

Use the current session as coordinator. Assess the product, design, technical, verification and handoff document groups; declare affected owners, canonical paths, dependencies and decision sources in the task. Use the existing role definitions in task scope without activating milestone roles or invoking stage-bound skills to bypass their checks. A completed milestone and null active role are valid context; they do not authorize a new milestone or a new product acceptance.

1. Find any matching unfinished task before creating one. Record the user request, concise plan, exact relative file scope, source paths, observable acceptance IDs and actual document impact assessment with `create --input`; do not copy template no-impact explanations as conclusions. Name required canonical writebacks and their responsibility roles in `document_tasks`. `start` before working. Task JSON is data, never shell text. Keep unrelated user edits intact.
2. Execute the scoped work. Do not ask the user to reconfirm a clear request or routine implementation details. Ask only about material ambiguity, changed product/technical constraints or missing authority. Use `checkpoint --summary --next` to save concrete progress before interruption, `revise` for a clarified bounded plan, or `block`/`escalate` with a concrete reason/target when work cannot remain bounded. Do not turn every such case into a new milestone.
3. Process affected upstream owners before implementation: `dispatch --document <id>` provides the role definition, input and bounded write scope. With authorization/runtime support, hand the packet to the matching specialist agent; otherwise fully read that role definition and perform its responsibility serially in the current session, recording the actual executor and mode. Workers are not alone in the codebase: own only assigned canonical paths and accommodate others' edits. Material unresolved choices remain pending. Update the actual product/design/technical documents and record the performed work with `reconcile`; a task summary alone is insufficient. Preserve original versions and do not extend an old milestone acceptance to new behavior.
4. Implement against the reconciled contracts, then run meaningful checks using `verify` with explicit argv arrays. Record inspection/manual observations using `observe`, with real evidence and accurate pass/fail/not_run. Cover each acceptance criterion; a lint/build exit code alone does not prove UI or business behavior. Follow any actual user/manual acceptance requirement. QA and handoff owners then update the canonical report/matrix/current entry and reconcile their work. Serial role processing is not independent QA; a dispatch packet or delegated authoring receipt alone is not independent verification.
5. Inspect the actual diff against scope, document impact and existing user work; use `revise` if another group is affected. Follow the protocol's context closeout section and [maintenance rules](../../../core/document-maintenance.md#6-上下文压缩的执行编排). Have each affected owner consolidate the canonical text: current decisions/reasons, final changes, effective test results, limitations, regression routes and retained IDs; repeated rounds and obsolete next actions leave default context while originals remain recoverable. Reconcile changed text again; concise documents need an actual no-further-cleanup assessment, not artificial edits.
6. Record semantic closeout with `compact --input`, covering every document responsibility and sourced decisions/retained items. Preserve existing retained IDs or provide evidenced dispositions. Then `finish` uses the reviewed outcome and requires current acceptance, owner receipts, closeout and recoverable originals. Treat stale synthesis as historical. Separate executor semantic review, static integrity and independent recovery; keep unrun recovery NOT_RUN, never claim an independent trial from fixture tests or metadata. No archive bundles or automatic extra agents are required.
7. Report the result, actual role execution, changed canonical documents, compaction/recovery status and task path. The tool checks structure and provenance, not semantic sufficiency. Keep plan/result in the task record and definitions in their authoritative groups. Follow existing commit/push authorization, stage only task files and cite the Q ID in commits. Report saved/committed/pushed separately; do not turn Quick into an automatic deployment flow.
