- 输入：用户本轮澄清为主要依据；[分享问答：提升 UIUX 设计能力](https://chatgpt.com/share/6aa4c64a-c63c-83e8-bcdc-880db2ed37a6)为参考。

## 1. 已确认目标与分析修正

用户明确指出：当前 UI/UX 产物对于 agt 的后续 agent 可用性差；前端连基础文案也会偏离，需要测试反复截图确认并经历十几轮重修。用户需要：

| 目标 | 状态 | 需要实现的结果 |
|---|---|---|
| G1：提高设计稿质量 | CONFIRMED | 设计本身在布局、视觉层级、文案表达、交互、响应式和完成度上达到本轮目标 |
| G2：提高设计到前端的交接质量 | CONFIRMED | 前端能直接定位并准确落实设计内容，基础偏差在开发阶段被发现，减少依靠 QA 反复补救 |
| G3：按用户要求整改、重构设计及产出 | CONFIRMED | 本轮要求决定设计目标和重构范围；失效的旧设计退出当前依据，相关产物一起更新 |

三项目标的共同衡量对象是：**后续 agent 能否找到唯一有效的设计来源，并准确实现当前要求。** 文档数量、截图数量和检查项数量不是成功指标。

撤销上一版计划中的两个不充分前提：

- 不再默认“已有设计方向就直接沿用、仅做增量检查”。用户已要求整改或否定旧方向时，应重新推导受影响设计，允许替换其结构和产物。
- 不再以“只新增一份文档”限制方案。文案需要可直接复用和比较的来源；是否新增文件取决于能否减少 agent 的猜测与重复转写。

本次把重点前移到设计产出的准确性、交接的可执行性和前端提交前的自检。下文保留方案依据；当前执行规则以[设计交付协议](../../core/design-delivery.md)、角色/Skill 和锁定 Profile 为准，实施及未验证范围见第 7 节。

### 参考问答摘要

讨论从网页缺少视觉特点、状态切换生硬，逐步走到设计、实现和验收的衔接：

1. 给设计过程补充参考、方向探索、视觉层次和有目的的动效。
2. 用浏览器呈现效果检查设计，形成修改反馈。
3. 缩短角色定义，把具体规则放在按需读取的资料中。
4. 以原型、Token 和结构化约束向前端交付，减少转述损失。
5. 前端保有技术实现空间，同时满足已确定的呈现与行为要求。
6. 验收结合视觉对比、交互证据和工程检查。

这些是[原问答提出的建议](https://chatgpt.com/share/6aa4c64a-c63c-83e8-bcdc-880db2ed37a6)，不是已经验证的效果保证。下文是基于当前仓库的独立分析与方案；原文中的工具趋势、评分和收益排名不作为已核实事实采用。

## 2. 实施前的差距分析

反复还原失败及基础文案偏差是用户报告的实际问题。下表记录基线 `d95f20c` 的规则差距，链接现在指向已修改文件。尚未独立复现具体产品；某次失败究竟来自漏读、混用版本、重新措辞还是其他原因，仍须在试点中定位。

| 环节 | 仓库现状与依据 | 本次建议补足 |
|---|---|---|
| UI/UX | [角色定义](../../roles/uiux/base.md)已有视觉方向确认、共享 Token、完整状态、原型与动画说明 | 补足视觉设计过程，以及下游能定位的准确内容、资源和状态定义 |
| 设计执行 | [UI/UX Skill](../../.agents/skills/agt-uiux-design/SKILL.md)要求本地预览和记录证据 | 规定设计稿可复现的打开方式、文案来源、页面/状态入口，以及整改时整套产物的同步更新 |
| 前端架构 | [架构角色](../../roles/frontend-architect/base.md)已禁止改变批准的视觉目标，要求将设计转为规格 | 按设计验收条目映射组件、状态和技术风险，提前发现还原冲突 |
| 前端实现 | [开发角色](../../roles/frontend-implementer/base.md)已有高还原、多分辨率检查及禁止改变交互含义 | 明确逐项读取和复用文案、布局、资源与状态；提交 QA 前自行检查基础还原 |
| 产品验证 | [质量角色](../../roles/quality/base.md)已有原型对比、UI 验证及禁止用审美偏好判缺陷 | 给出可执行的设计验收条目、证据口径和问题归属 |
| 交接 | [交接模板](../../templates/role-handoff.md)已有输入版本、自检、证据和未决项 | 让 agent 从当前版本定位具体页面、区域、文案和状态，不依赖聊天记忆或泛化摘要 |
| Profile | [consumer-ai-web](../../profiles/consumer-ai-web/PROFILE.yaml)要求主题、原型、交互、响应式及交接产物 | 如引入独立设计规格，应明确必需路径与升级影响 |
| 设计变更 | [共同契约](../../core/role-contract.md#requirement-confirmation)已要求撤销被纠正的旧理解，工作流已有回溯 | 明确设计重构的影响范围、当前产物替换和旧版本退役，防止保留历史被误解成继续沿用旧标准 |

判断：需要补足的是**高质量设计输出 → agent 可直接使用的交接 → 前端首次实现与自检 → 设计变更后整套依据同步替换**。角色划分与阶段体系可以复用。

## 3. 融入原则与取舍

### 3.1 采用哪些能力

- **从本轮目标出发**：先读取用户当前要求，辨认仍有效的业务/品牌约束和已被否定的旧设计。旧原型用于识别现状；能否复用取决于它是否满足当前目标，不能因旧版曾批准就继续作为整改标准。
- **有依据的视觉方向**：结合有效品牌约束和参考分析构图、字体、色彩及层次；有真实方向分歧时探索 2–3 个代表性方案。已明确的整改要求直接进入设计，不再次索取相同授权。
- **视觉设计责任**：设计师解释主任务、视觉焦点、信息层级、字体节奏和表面关系。相关约束必须服务产品目标，不能只写“高级”“有质感”。
- **状态变化的显式决定**：关键交互说明需要何种过渡，或为何即时切换；需要动效时定义触发、起止状态、时长/缓动来源、中断和减少动效行为。
- **浏览器证据**：设计阶段检查实际原型；实现阶段检查实际产品。截图用于静态呈现，交互观察、录屏或适用的浏览器断言用于时间过程。
- **统一验收依据**：设计、架构、开发和质量角色使用同一组批准条目；工程实现选择不能隐式重定义结果。
- **准确内容优先**：固定文案、控件数量/顺序、资源和状态内容必须有可读取来源；前端直接复用或转换，不能凭截图重写措辞、漏掉提示或自行换图。
- **前端负责提交质量**：内容、结构、样式与交互先在开发阶段自检；QA 保留独立验证职责，不承担发现所有基础偏差的第一道检查。

减少动效应成为设计约定的一部分。W3C 对交互触发动画的说明支持关闭非必要运动及尊重系统偏好；该条款为 WCAG 2.2 的 AAA 项，本方案不据此宣称产品已经符合完整 AAA。[W3C：Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

### 3.2 不直接照搬的规则

| 规则方向 | 在 agt 中的处理 | 原因 |
|---|---|---|
| 禁止纯色、卡片、常见组件或特定 CSS 工具风格 | 改为检查是否符合本产品的批准目标 | 这些形式本身不能证明质量低；极简和高信息密度场景可能适用 |
| 所有切换必须有动画 | 要求显式决定并验证，允许有依据的即时切换 | 高频操作、性能和减少动效偏好需要不同处理 |
| 每次都做三套完整方案 | 仅在新方向或实质分歧时做有限探索 | 避免对既定设计重复发散 |
| 主观评分低于某分数就阻塞 | 缺陷绑定批准要求和证据；审美建议单列 | 没有标定的评分不适合作为硬门槛 |
| 新增独立视觉评审角色及阶段 | 先由 UI/UX 自检和现有质量角色承担 | 当前已有职责覆盖，尚无增加编排复杂度的证据 |
| 自动循环修改直到“足够好看” | 完成当前批准要求后交付；新审美目标另行确认 | 防止验收目标移动和无限返工 |

这些选择遵循已有[最小充分交付规则](../../core/role-contract.md#no-speculative-overengineering)。本次不建议建立参考素材平台、专用截图服务、全局动画库或新的评分系统。

### 3.3 方案比较

| 方案 | 收益 | 代价/缺陷 | 建议 |
|---|---|---|---|
| 只扩充 UI/UX 角色文字 | 改动少，能提示更多设计维度 | 无法保证下游读取、保留和验收这些要求 | 不作为完整方案 |
| 精简角色入口＋可复用设计来源＋明确接收/重构规则 | 同时覆盖设计质量、准确实现和版本替换 | 需要同步四个专业角色及相关入口 | **推荐** |
| 新角色、多份设计文档、机器 Schema 与自动评分流水线 | 可能支持更大规模自动化 | 当前缺少真实规模和失败数据支持 | 暂缓 |

## 4. 推荐结构与责任边界

本次新增两个基座文件：

- `core/design-delivery.md`：维护准确交接、前端接收与自检、设计重构及版本替换规则。只由 UI/UX、前端架构、前端实现和质量角色按需读取；不加入所有角色的必读上下文。
- `templates/design-spec.md`：提供产品 `design/design-spec.md` 的模板，并内含文案数据格式示例。索引必须能定位具体原型区域、内容键、资源和状态；泛泛的“保持高还原”不构成交接。

Profile 2.0.0 要求产品新增设计规格和可复用文案源两项，其余沿用既有产物。文案采用简单 JSON，不引入专用规格语言或平台；本次未生成或修改任何具体产品产物：

| 产品产物（相对当前里程碑目录） | 维护内容 | 真源边界 |
|---|---|---|
| `design/design-spec.md`（新增） | 当前设计版本、目标、页面/区域/状态索引、固定约束和检查条件 | 后续 agent 的任务入口，链接准确来源而非转述大段设计 |
| `design/copy.json`（新增） | 固定文案键值、动态文案模板及变量含义 | 原型和前端使用同一语义来源；不把真实业务数据固定成展示文案 |
| `design/theme.css` | 实际 Token 值及必要语义注释，包括适用的层次与动效 Token | 数值不在多份文档重复维护 |
| `design/prototype/index.html` 及资源 | 可运行、可定位页面和状态的设计表达；消费文案源 | 记录启动命令、入口、资源和示例数据；前端读取 HTML/CSS 细节，优先复用或忠实转换 |
| `design/interactions.md` | 触发、状态、过渡、反馈、中断和错误处理 | 状态行为及 Motion 的详细定义 |
| `design/responsive-accessibility.md` | 目标视口、布局变化、键盘、焦点及减少动效规则 | 响应式和可访问性详细约束 |
| `handoffs/uiux.md` | 当前版本、可实现范围、失效版本、条目入口和未决项 | 区分正在整改与可供实现的版本；不再创建第二份交接正文 |
| `technical/frontend.md` | 设计条目到组件、状态和实现策略的映射 | 技术方案由前端架构角色维护 |
| `implementation/frontend-validation.md` | 文案/结构/样式/状态自检、设计差异及证据引用 | 前端在提交 QA 前完成；已知基础偏差先自行修复 |
| `verification/coverage-matrix.md`、`report.md`、`uat.md` | 独立验证结果、问题归属及人工验收步骤 | 验证结论与设计要求分开保存 |

`design-spec.md` 内按 `PAGE-*` / `CAP-*` 组织局部验收 ID，例如 `UIA-PAGE-001-01`；这是建议的设计条目标识，不引入新的全局需求系统。详细状态、Token 和响应式条目使用链接引用，避免四处复制。

职责划分：

- UI/UX 按用户当前目标定义结果，维护原型、文案及规格的一致性；设计整改覆盖全部受影响产物。
- 前端架构在既定产品约束下评估实现路径，记录性能、依赖和可访问性冲突。
- 前端开发在**已批准技术方案内**选择实现细节；忠实移植设计，不重新创作文案或界面。组件拆分、DOM 或 CSS 手段可以不同，但准确内容、顺序、状态和呈现必须满足当前契约。
- QA 验证实际结果，区分确定缺陷、待澄清项、未验证项及改进建议。不得为了匹配实现而修改设计基线。
- 守门器沿用现有规则检查产物、批准、阻塞及证据，不判断页面是否好看。

用户明确的新要求决定下一版设计目标，并在相应范围撤销旧要求；文件修改时间本身不能证明新要求已落实或设计已批准。原型、文案、规格和 Token 若有冲突，由设计责任方统一修正；前端不从多个版本中自行拼选。参考站点是灵感来源，不能成为未经确认的验收要求。

## 5. 让前端直接落实设计，先消除基础偏差

### 5.1 文案有精确来源，并直接用于原型和实现

固定标题、按钮、说明、占位提示、空态、错误提示，以及有独立要求的可访问名称，都要能定位到原文。以下仅示范结构，不向产品增加功能：

```json
{
  "static": {
    "generation.submit.label": "开始生成",
    "generation.empty.title": "还没有生成内容"
  },
  "templates": {
    "generation.usage": "已使用 {used} / {limit} 次"
  }
}
```

- 原型消费该来源，前端将它导入或转换为工程中的文案资源，避免手工再写一份；实际产品不需要在运行时访问 `.planning/`。
- 工程中如需生成副本，记录源设计版本和转换方式，副本不成为第二个手工维护的真源；已有国际化资源可以承接结果，不为此强制引入国际化框架。
- 静态文案按批准文本核对用词、标点和明确要求的换行；“开始生成”被改成“立即创建”属于偏差。浏览器空白折叠等比较规则需明确，不能用同义改写或宽松归一化掩盖差异。
- 动态文案定义变量含义、格式与代表性样例；真实 API/用户/AI 内容通过既有应用模型进入界面，不固定成原型中的示例值。前端不因此绕过 DTO 转换边界。
- 设计规格按页面/区域/状态引用文案键，说明出现位置、顺序和条件；只提供一份无位置关系的字符串表仍不足以交接。

### 5.2 交接要让接收 agent 可以打开、定位、复现和转换

每个交付页面应能回答：

| 接收时要查的问题 | 必需来源 |
|---|---|
| 当前该实现哪个版本？ | 当前交接中的设计 revision/快照、批准范围及失效版本指针 |
| 原型怎么打开，状态怎么进入？ | 启动方法、页面入口、操作步骤或场景入口、确定性示例数据 |
| 区域、控件和文字是什么？ | 原型文件及区域标识、文案键、元素数量/顺序和显示条件 |
| 具体样式和资源从哪里来？ | 原型 HTML/CSS、共享 Token、实际图片/图标/字体文件及使用位置 |
| 哪些行为和布局不能改？ | 当前交互、响应式定义及验收条目 |
| 哪些地方尚未定义或无法复现？ | 明确的缺口与受影响范围，不能让前端自行猜补 |

前端在编码前完成这项接收核对，并在既有方案/自检记录中留下来源。它是开发步骤，不新增一个审批阶段。输入冲突只阻塞受影响内容，其他明确部分可以继续。

### 5.3 前端采用忠实转换，并对首次提交负责

1. 读取源原型、文案、样式和交互；不能仅凭一张截图或交接摘要重画页面。
2. 优先复用可用 Token、资源、样式及结构，按批准技术方案转换为工程组件并接入数据。复用代码只是手段，产出仍须符合语义、数据边界和可访问性约束。
3. 先完成一个代表性页面/区域的内容、布局、状态和视觉核对，再推广共享组件，避免错误模板批量扩散；不增加逐页用户审批。
4. 在提交 QA 前按下表自检、修复偏差。无法执行的检查记录为未验证，不能把浏览器结果写成已通过。

| 顺序 | 前端自检内容 | 证据/方法 |
|---|---|---|
| 1 | 文案、控件、提示、资源是否缺漏/多出/错位 | 从固定设计版本取期望值，检查运行页面对应区域的实际文本、可见性、数量与顺序 |
| 2 | 布局、字体、间距、色彩、层次和响应式 | 读取原型样式及约束，检查运行页面，并与同条件原型对照 |
| 3 | 正常、加载、空态、失败等已定义状态 | 使用契约一致的场景数据复现，核对内容和交互 |
| 4 | 过渡、中断、焦点和减少动效 | 实际交互、录屏或适用的浏览器断言；静态截图不能证明时序正确 |

文案与元素结构的检查应针对用户报告的失败模式自动化，优先使用产品已有浏览器测试能力。期望值来自固定版本的设计来源，不能从实现资源反向生成；测试还要验证内容确实出现在正确状态和位置，不能只比较两份 JSON 是否相同。

基础自检通过后，QA 再做独立的设计还原和产品行为验证；匹配版本的开发证据可复用。截图仍用于必要的视觉检查，但文案错字、缺少按钮等确定问题应能直接定位来源并修复，无需靠多轮肉眼找差异。

截图比较记录浏览器、系统、视口、DPR、字体、数据及页面状态，按具体场景设置容差。环境会影响渲染，因此应保持对比条件一致。[Playwright：Visual comparisons](https://playwright.dev/docs/test-snapshots)

首次还原以批准设计为依据；直接将当前实现截图保存为基线不能证明正确。设计效果检查、动态行为检查和静态视觉检查分别记录，不能用单一截图分数代替。

## 6. 用户要求整改时，重构受影响设计和整套产物

### 6.1 当前要求决定目标，旧设计提供历史

用户要求整改、重构或否定旧方向时，设计师先根据本轮目标重新判断页面职责、信息组织、布局、文案、组件、视觉和交互。可以复用符合新目标的部分，也可以重做结构；不以保留旧布局、旧组件或最小代码差异为优先目标。

已经明确的要求直接作为整改输入，不因旧版曾批准而重复询问是否允许修改。不明确且会改变结果的部分才澄清；用户要求设计重构也不意味着自动增加业务能力或修改无关产品范围。

### 6.2 一次整改覆盖完整依赖

按以下顺序执行，并把结果就地更新到现有主文档与交接：

1. 提取用户当前要求，指出被替代的旧假设、受影响页面/状态，以及仍有效的约束。
2. 在覆盖当前产物前保留可恢复的旧版本或快照。旧审批仍作为历史证据，不能冒充新版批准。
3. 按新目标重构必要的原型、文案、Token、资源、交互和响应式定义；涉及共享组件时检查所有使用位置。
4. 同步重写设计规格和交接，移除当前正文中失效的规则、文案、资源引用及验收预期，避免新旧规范并列供下游猜选。
5. 对照新目标检查整套产物的一致性；列出受影响的前端方案、实现和测试预期，由对应角色更新，设计师不越权改实现。
6. 对仍需批准的新版内容明确标注待审范围；批准后更新可供实现的设计版本。前端与 QA 重新核对版本，只在受影响范围重做实现和验证。

整改期间，已被用户否定的旧条目立即标为失效/待替换，不能因新版尚未完成而继续实现。新版草稿也不能自动标为已批准。受影响内容等待设计补齐，未受影响内容可继续。

“保留历史”与“当前设计必须增量修改”是两回事。Git 或冻结快照负责追溯；当前入口只指向当前有效产物。原有证据保留原版本归属，不直接用于宣称新版通过。

例如，用户要求把卡片式概览改为围绕主任务展开的工作区，设计师应按此目标重新组织页面，并同步重写文案、原型和交接；前端不能继续以旧卡片网格或旧文案验收。若用户仅改一个按钮文案，则更新该文案及相关引用即可，范围由本轮要求决定。
